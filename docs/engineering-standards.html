0. 文档定位与证据边界（请先读）

本规范的素材来自两类完全不同性质的来源，使用前必须分清楚：

  1. anthropics/claude-code 官方 GitHub 仓库 —— 核实后确认它不包含产品源码，只是发布 / Issue 跟踪仓库（README 只有安装方式和数据政策，没有 CONTRIBUTING.md、没有 commit 规范、没有架构文档；仓库里的 CLAUDE.md 只是它自己 CI 的安全护栏说明）。因此本规范不存在"抄 Claude Code 官方贡献指南"这件事。
  2. 第三方逆向分析 —— learn-claude-source 网站对 Claude Code v2.1.88 编译产物的逆向整理（作者声明"仅用于学习研究目的"），以及本仓库 docs/claude-code-parity/ 下对本地 Claude Code 2.1.87 参考源码（1,902 个文件、51 万行）做的逐文件结构扫描 + 关键路径人工阅读。这两类都是二手整理，不是逐行语义审计。
本文档的性质：从"可观察到的工业级 Agent 产品长什么样"中提炼出的可迁移设计模式与工程纪律，不是对 Claude Code 源码的复制，也不是官方规范的转述。

docs/claude-code-parity/{README,core,interaction,integrations,discussion}.md 是本仓库代码与参考材料的能力对照表，比本文档更具体、更新更频繁，是重构 backlog 的来源；本文档只负责"规则"层。

已知过期点：core.md 判定"长会话压缩 = 缺失"，但 apps/sidecar/src/services/conversation-context.ts 现已实现分段摘要压缩（滚动摘要 + 预算裁剪 + 失败熔断）——代码演进快于文档，使用对照表前请先核实文件是否仍存在、行为是否仍如文档所述。

1. 核心设计理念

五条贯穿工业级 Agent 系统的核心认知（源自 learn-claude-source 概览页五点洞察，经适配）：

  1. Agent 的本质是 while 循环 + 工具调用，其余复杂度都是叠加在循环之上的工程纪律。对应 packages/agent-core/src/agent.ts 的 runAgent。
  2. 一切皆 Tool：文件读写、Shell、子代理委派、未来的 MCP 都应是同一个 Tool 接口的实现。
  3. 权限是架构的第一等公民，检查点必须在执行之前，默认值必须 fail-closed。
  4. 上下文窗口是稀缺资源，必须用分层策略主动管理。
  5. 异步生成器是流式与可中断性的标准范式，优于回调或轮询。

与 ~/.maestro/workflows/coding-philosophy.md 中"数据结构优先""拥抱简单"等通用原则不冲突：前者是通用编码哲学，这里是 Agent 系统的领域特定补充。

2. 十条可迁移设计模式与落地规则

#模式解决的问题AgentDesk 现状落地建议
1统一 Tool 接口新增能力不应改动 Agent Loop 本身tools.ts:66 已有 AgentTool/defineTool，ToolRegistry.select 支持命名空间通配新工具一律通过同一接口注册；禁止在 orchestrator.ts 里为某个工具开特例分支
2权限三态 + fail-closed二元 allow/deny 表达不了"需要询问"agent.ts:309 已有 safe/confirm/dangerous 三级 risk，但只覆盖 shell.run，无 deny 规则扩展规则模型为 {tool, scope, pattern, decision}；deny 永远优先于 allow；新工具默认 dangerous
3分层上下文压缩长任务耗尽上下文窗口，截断不可逆丢信息conversation-context.ts 已有阈值触发的滚动摘要 + 预算裁剪 + 失败熔断补齐"每轮保留最近 N 条完整工具结果"的 micro 层；摘要用结构化字段；压缩前先落盘原始转录
4子代理即分治子任务中间步骤不应污染主任务上下文orchestrator.ts:164/180 已支持委派，子 Run 独立事件流子代理从空消息列表起步；只回传最终产物；工具集中绝不包含"派生子代理"的工具
5Hook 洋葱模型需在不改源码前提下插入审计/拦截/改写逻辑目前只有单点审批，无通用 Pre/PostToolUse在 executeToolCall 前后引入可配置 hook；顺序固定 validate → Pre → permission → call → Post
6异步生成器驱动流式实时反馈与中断不应靠回调/轮询agent.ts:126 的 stream() + emit 回调新链路优先用 async function*；中断统一走 AbortSignal
7两层按需加载工具/技能增多时系统提示词不能线性膨胀skills.ts 已有目录摘要 + 按需加载全文工具变多后比照同一模式：核心常驻，其余按需取 schema
8Append-only 持久化高频写入需要性能和 crash 安全tasks.ts 状态机已用 SQLite会话转录类数据优先 JSONL 追加写 + 元数据分文件
9Fail-closed 默认值"忘记声明"不能等于"允许"部分工具已显式声明默认分支统一走拒绝/不安全，用集中 DEFAULTS 常量表达
10适配器模式扩展外部能力接入外部协议不应为每个服务单独写分发逻辑全仓库未发现 MCP 相关代码（已核实缺失）工具命名加来源前缀防冲突；单个外部连接失败要隔离

"现状"列的文件:行号来自对当前代码的直接核实；重构前请用 git log -p 或重新 Grep 复核。

3. 目录结构规范

3.1 Monorepo 顶层约定（现状，继续保持）

AgentDesk/ ├── apps/ │ ├── desktop/ # Tauri + React 桌面端 UI │ ├── sidecar/ # Node/Hono 常驻后端：Agent 执行、HTTP/SSE API │ └── cli/ # Ink 终端客户端 ├── packages/ │ ├── agent-core/ # Agent Loop / Tool Registry / Orchestrator 核心库 │ ├── shared/ # 跨包契约（Zod schema + 推导类型） │ ├── integrations/# 第三方能力适配 │ ├── ui/ # 可复用 UI 组件 │ └── workflow/ # 可视化工作流相关 ├── docs/ │ ├── claude-code-parity/ # 能力对照 backlog │ └── engineering-standards.md # 本文档：规则层 └── scripts/ # 构建/发布/校验脚本

依赖方向只能是 apps/* → packages/*、packages/agent-core → packages/shared，禁止 packages/* 反向依赖 apps/*。

3.2 新增能力时的标准落点

要新增的东西放在哪必须同时做的事
新的 Agent 工具packages/agent-core/src/tools.ts + 具体实现放对应 service声明并发安全/风险等级；补单测
新的 HTTP 路由apps/sidecar/src/http/routes/<domain>.ts一路由一文件
新的跨包契约类型packages/shared/src/contracts/<domain>.tsZod schema + 类型推导，不要在业务包重复定义
新的桌面功能apps/desktop/src/features/<feature>/按 feature 分目录，不按组件类型分目录
新的技能技能目录下 SKILL.mdMarkdown + frontmatter，不用 JSON

3.3 命名约定

  • 文件名：TS/TSX 源文件 kebab-case.ts；React 组件文件可用 PascalCase.tsx
  • 类型/接口：PascalCase；Zod schema 常量：同名 camelCase
  • 函数/变量：camelCase；未使用变量加前缀 _

4. TypeScript / 代码风格规范

4.1 现状（继续保持，不允许放松）

  • strict + noUncheckedIndexedAccess + noImplicitOverride + noFallthroughCasesInSwitch + verbatimModuleSyntax
  • @typescript-eslint/consistent-type-imports: error
  • no-console：只允许 warn/error/info
  • React Hooks 规则仅在 apps/desktop、apps/cli、packages/ui 生效

4.2 新增纪律

  • 安全相关属性一律显式声明，不依赖默认值隐式放行
  • 工具/服务函数是完整对象（schema + 风险标注 + 执行 + 结果上限），不是裸函数
  • 错误处理统一走 AppError/ErrorCode（@agentdesk/shared）
  • 注释解释"为什么"而非"是什么"
  • 不写占位实现而不说明；需要占位时在代码中明确标注

5. Git 提交规范

项目已通过 commitlint.config.js（@commitlint/config-conventional）强制 Conventional Commits。

<type>(<scope>): <简短中文描述>

[可选正文：说明动机/背景，而不是复述 diff]
  • type：feat fix refactor docs test chore
  • scope：受影响的包/应用名，如 desktop sidecar cli agent-core shared code projects
  • 描述用简体中文，动宾结构，说明做了什么/为什么，而不是复述 diff
反例：历史上出现过一次 commit subject 直接是未解析的 JSON 字符串（如 {"subject": "feat(projects): ..."}）——说明自动生成 commit message 的流程没有正确解包成纯文本。任何自动化提交流程都要在写入前校验"最终字符串不包含 JSON 结构字符"。

示例

feat(agent-core): 为工具调用增加并发安全标注

只读工具默认允许并发批处理，写操作形成顺序屏障，避免 Promise.all 无差别并行导致的文件竞争。
fix(sidecar): 修复长会话压缩后工具调用与结果配对丢失的问题

6. Agent 专项规则 Checklist（重构时逐项核对）

动手前请先用 Grep/Read 核实差距是否依然存在，不要凭记忆判断。

  • 工具执行顺序：只读工具可并发，写操作是否已形成顺序屏障？
  • Shell 风险分类：git branch -D/-m、git fetch 等是否仍被宽泛前缀白名单误判为安全？
  • 权限规则是否仍只覆盖 shell.run，缺少 fs.write/deploy.run 等其他高风险工具的持久规则？
  • 长会话压缩是否已有"失败熔断/分级回退"，而不是压缩失败就崩溃？
  • 子代理委派的工具集中是否意外包含了"派生子代理"的工具（递归爆炸风险）？
  • 技能 allowed-tools 字段解析成功是否被误当成"工具权限已强制执行"？
  • 跨端（CLI/桌面）审批是否存在重复提交、或一端处理后另一端仍在等待本地输入的问题？

7. 这份文档怎么用

  1. 动手重构/写新功能前，先读第 2、6 节确认适用的模式和 checklist；再读 docs/claude-code-parity/ 对应文件确认差距是否仍然存在。
  2. 本文档描述的是规则，不是任务清单。具体做哪个 backlog 项由每次任务单独确认范围。
  3. 规则更新：直接编辑本文件并在 git 提交信息里说明原因，不要另建互相矛盾的规范文档。
  4. 与 docs/claude-code-parity/ 的分工：这里是"为什么这样做"的规则层；那边是"现在做到哪一步了"的证据层。两者都过期时以重新核实代码为准。
